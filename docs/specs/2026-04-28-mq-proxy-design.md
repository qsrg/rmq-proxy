# MQ代理系统设计文档

## 1. 概述

### 1.1 背景

当前系统使用RocketMQ作为消息中间件，随着业务发展，存在以下需求：
- 后续可能需要替换底层存储实现或自研MQ系统
- 希望在替换后端时对上层应用透明，减少迁移成本

### 1.2 目标

构建一个MQ代理系统，实现：
1. **协议兼容**：完全兼容RocketMQ 4.9原生协议，现有RocketMQ客户端无需修改代码即可接入
2. **透明代理**：作为协议代理层，便于后续替换后端存储实现
3. **双轨接入**：支持RocketMQ原生客户端和proxy-SDK两种接入方式
4. **平滑迁移**：后端存储替换时，使用proxy-SDK的客户端无需任何修改

### 1.3 适用范围

| 维度 | 选择 |
|------|------|
| 迁移场景 | RocketMQ → 自研MQ |
| 系统规模 | 中规模（100万-1000万/天，1-3集群，50-200 Topic） |
| 自研MQ状态 | 先搭建代理层，后续开发存储 |
| 核心功能优先级 | 消息收发（普通消息）第一批 |
| 部署形态 | 独立代理集群 |

### 2.2 核心组件职责

| 组件 | 职责 | 关键接口 |
|------|------|---------|
| **协议适配网关** | 接收不同协议的客户端连接，转换为内部消息模型 | ProtocolHandler |
| **核心消息引擎** | 消息路由、编解码、流控 | MessageEngine |
| **存储抽象层** | 屏蔽后端存储差异，提供统一存储接口 | StorageAdapter SPI |
| **存储适配器** | 实现具体存储的读写逻辑 | 各存储自行实现 |

### 2.3 设计原则

1. **协议完整性**：RocketMQ 4.9协议支持必须完整
2. **无状态代理**：代理节点无状态，可水平扩展，不存储消息数据
3. **故障隔离**：后端存储故障不影响代理层，快速失败+熔断
4. **可观测性**：协议层全链路埋点，支持迁移前后对比验证

## 3. RocketMQ 4.9协议兼容设计

### 3.1 RemotingCommand协议帧结构

RocketMQ 4.9使用统一的RemotingCommand作为所有网络通信的载体。

**协议帧编码结构**：

```
+----------------+------------------+------------------+------------------+
|  Total Length  | Header Length    |   Header Data    |    Body Data     |
|   (4 bytes)    | (4 bytes,含类型) |    (变长)        |     (变长)        |
+----------------+------------------+------------------+------------------+

- Total Length (4字节): 整个帧长度（不含自身）
- Header Length (4字节): 高8位存储序列化类型，低24位存储header长度
- 序列化类型: JSON(0) 或 ROCKETMQ(1)
- Header Data: RemotingCommand序列化后的数据
- Body Data: 消息业务数据
```

**RemotingCommand核心字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 请求码/响应码，区分不同业务操作 |
| language | LanguageCode | 语言代码，默认JAVA |
| version | int | 协议版本号 |
| opaque | int | 请求唯一标识（自增ID），用于请求响应匹配 |
| flag | int | 标志位（bit0=RPC类型，bit1=是否单向） |
| remark | String | 备注/错误信息 |
| extFields | HashMap | 扩展字段，承载业务参数 |
| customHeader | CommandCustomHeader | 自定义头部（业务Header） |
| body | byte[] | 消息体数据 |
| serializeTypeCurrentRPC | SerializeType | 序列化类型（JSON/ROCKETMQ） |

**Flag标志位解析**：

| 标志位 | 说明 |
|--------|------|
| RPC_TYPE (bit 0) | 0=请求，1=响应 |
| RPC_ONEWAY (bit 1) | 是否单向调用（无响应） |

### 3.2 协议栈分析

| 协议层 | 描述 | 代理策略 |
|--------|------|---------|
| **NameServer协议** | 路由发现、Topic元数据查询 | **完全代理**：代理层维护路由表，屏蔽后端拓扑变化 |
| **Broker协议** | 消息发送、拉取、确认 | **透传+增强**：协议帧解析后转发，可插拔拦截器增强 |
| **Admin协议** | Topic创建、删除、查询状态 | **重写实现**：映射到存储适配器的管理接口 |

### 3.9 序列化类型适配

RocketMQ 4.9支持两种序列化类型：

| 类型 | 值 | 说明 | 适配要求 |
|------|-----|------|---------|
| JSON | 0 | JSON序列化 | 必须支持 |
| ROCKETMQ | 1 | RocketMQ自定义序列化（更高效） | 必须支持 |

**适配建议**：代理层应优先支持JSON序列化（调试友好），后续扩展支持ROCKETMQ序列化（性能优化）。

### 3.10 客户端启动流程

```
客户端          Proxy          NameServer(后端)       Broker(后端)
  │               │                  │                  │
  │ ① 客户端启动  │                  │                  │
  │               │                  │                  │
  │ ── 心跳/注册─▶│                  │                  │
  │               │ ── 注册请求 ───▶ │                  │
  │               │ (Proxy作为虚拟    │                  │
  │               │  Broker注册)     │                  │
  │               │                  │                  │
  │               │◀─ 注册成功 ───── │                  │
  │               │                  │                  │
  │               │ ◀ 维护虚拟路由表 │                  │
  │               │   (Proxy对客户端 │                  │
  │               │    返回自己地址) │                  │
  │               │                  │                  │
  │◀─ 启动成功 ──│                  │                  │
  │               │                  │                  │
```

**关键点**：
- 客户端只知道Proxy地址，不知道真实Broker/NameServer
- Proxy向真实NameServer注册为"虚拟Broker"
- Proxy维护虚拟路由表，返回给客户端

## 4. 存储抽象层设计

### 4.1 存储抽象层定位

| 职责 | 说明 |
|------|------|

## 5. proxy-SDK设计

### 5.1 proxy-SDK定位

| 特性 | RocketMQ原生SDK | proxy-SDK |
|------|-----------------|-----------|
| 接入方式 | 使用RocketMQ协议连接Proxy | 使用自定义协议连接Proxy |
| 功能范围 | 原生RocketMQ功能 | 增强功能（监控、追踪、高级配置） |
| 迁移成本 | 后端替换无需改动 | 后端替换只需SDK内部切换 |
| 适用场景 | 被动迁移，不想改动代码 | 主动迁移，愿意投资未来 |

### 5.4 proxy-SDK增强功能

| 增强功能 | 价值 |
|----------|------|
| 消息轨迹追踪 | 全链路追踪，消息从发送到消费的完整路径，用于排查消息丢失、延迟问题 |
| 业务上下文传递 | 携带业务元数据，不侵入消息体，如：订单ID、用户ID、业务类型 |
| 智能路由 | SDK内部可根据Topic自动选择最优路径，减少应用层配置复杂度 |
| 监控埋点 | SDK自动上报监控指标，发送成功率、延迟、异常 |
| 配置热更新 | 无需重启，动态更新配置，Topic路由、限流阈值、超时参数 |
| 故障自动切换 | SDK感知Proxy故障，自动切换到备用节点，提升应用层可用性 |

### 5.5 SDK与原生SDK共存策略

两种接入方式可以在同一应用中共存：

```
应用系统
│
├── 核心业务模块
│   │ 使用proxy-SDK
│   │ - 需要消息追踪
│   │ - 需要监控埋点
│   │ - 愿意投资未来
│   │
│   └── 订单服务
│       └── 订单消息
│           └── proxy-SDK → Proxy → 自研MQ
│
├── 普通业务模块
│   │ 使用RocketMQ原生SDK
│   │ - 不想改动代码
│   │ - 功能够用即可
│   │ - 暂时不迁移
│   │

│   │   └── RocketMQ原生SDK → Proxy → RocketMQ

    │ 按Topic逐步迁移，不一刀切
```

## 6. 迁移策略设计

### 6.1 迁移阶段规划

```
阶段0：准备阶段 (1-2周)
阶段1：双轨运行阶段 (2-4周)
阶段2：灰度切换阶段 (4-8周)
阶段3：全量切换阶段 (1-2周)
阶段4：清理阶段 (1周)
```

### 6.2 阶段0：准备阶段

**目标**：确保迁移所需的基础设施到位

**工作内容**：
1. Proxy集群部署：搭建独立代理集群，配置RocketMQ适配器，验证协议兼容性
2. 自研MQ适配器开发：实现StorageAdapter接口，连接自研MQ存储，本地验证基本功能
3. 监控与验证工具准备：消息轨迹追踪系统、数据一致性比对工具、回滚预案演练
4. Topic盘点与分组：按重要性分类（核心/重要/普通），制定迁移顺序（普通→重要→核心）

**完成标志**：
- Proxy集群稳定运行
- RocketMQ适配器功能验证通过
- 自研MQ适配器开发完成
- 监控工具可用
- Topic迁移计划制定完成

### 6.3 阶段1：双轨运行阶段

**目标**：自研MQ适配器接入，不影响业务

**数据流**：
```
                    ┌─────────────────┐
                    │   Proxy集群     │
                    │                 │
                    │  ┌───────────┐  │
                    │  │ 双写开关  │  │
                    │  └───────────┘  │
                    └─────────┬───────┘
                              │
            ┌─────────────────┴─────────────────┐
            │                                   │
    ┌───────▼───────┐                   ┌───────▼───────┐
    │ RocketMQ      │                   │ 自研MQ        │
    │ 适配器        │                   │ 适配器        │
    │ (主路径)      │                   │ (校验路径)    │
    └───────────────┘                   └───────────────┘
            │                                   │
    ┌───────▼───────┐                   ┌───────▼───────┐
    │ RocketMQ      │                   │ 自研MQ        │
    │ 存储          │                   │ 存储          │
    │ (生效)        │                   │ (验证)        │
    └───────────────┘                   └───────────────┘
```

**消息写入流程**：
- 主路径：RocketMQ适配器 → 写入RocketMQ → 返回结果给客户端
- 校验路径：自研MQ适配器 → 写入自研MQ → 仅记录，不返回给客户端 → 后台比对一致性

### 6.4 阶段2：灰度切换阶段

**目标**：逐步将Topic流量切换到自研MQ

**切换顺序**：
- 第一批：普通Topic（非核心业务），预期风险低，验证周期1周
- 第二批：重要Topic（影响部分用户），预期风险中，验证周期2周
- 第三批：核心Topic（关键业务），预期风险高，验证周期4周+

**单个Topic切换流程**：
1. 配置切换（Topic路由调整）：Topic主路径从RocketMQ切换到自研MQ
2. 流量观察（监控指标）：监控发送成功率、延迟、消费成功率、消费延迟、消息积压
3. 消费验证（数据一致性）：消息计数比对、消息内容抽样、消费进度比对、轨迹追踪验证
4. 全量切换（确认稳定）：确认监控指标稳定、数据一致性验证通过、业务方确认无异常

### 6.5 阶段3：全量切换阶段

**目标**：所有Topic流量切换到自研MQ

**切换确认清单**：
1. 所有Topic切换完成确认：逐一确认Topic已切换，业务方确认功能正常
2. 回滚开关保留：保留RocketMQ适配器配置，可快速切回（分钟级）
3. 监控指标稳定：连续1周无异常告警，性能指标符合预期
4. 业务验收：核心业务方验收确认，用户反馈无异常

### 6.6 阶段4：清理阶段

**目标**：清理旧资源，完成迁移

**清理内容**：
1. RocketMQ适配器下线：从Proxy配置中移除，保留代码备用
2. RocketMQ数据归档：历史消息数据归档，消费进度数据导出
3. RocketMQ集群下线：停止接收新消息，保留集群一段时间，最终下线
4. Proxy配置简化：移除双写配置，移除灰度配置，简化为单后端模式

### 6.7 回滚策略

**触发条件**：
1. 自研MQ出现重大故障（存储异常、性能骤降）
2. 监控指标持续异常（成功率下降 > 10%）
3. 业务方反馈严重问题（数据丢失、消费异常）

**回滚流程**：
```
                    ┌─────────────────┐
                    │  回滚决策       │
                    │  (触发条件判断) │
                    └─────────┬───────┘
                              │
                              │ 决策回滚
                              │
                    ┌─────────▼───────┐
                    │ Proxy配置更新   │
                    │ Topic路由切回   │
                    │ 自研MQ → RocketMQ
                    └─────────┬───────┘
                              │
                    ┌─────────▼───────┐
                    │ 消费进度同步    │
                    │ 自研MQ进度 →   │
                    │ RocketMQ进度   │
                    └─────────┬───────┘
                              │
                    ┌─────────▼───────┐
                    │ 流量切回        │
                    │ Proxy → RocketMQ│
                    └─────────┬───────┘
                              │
                    ┌─────────▼───────┐
                    │ 验证恢复        │
                    │ 监控指标确认    │
                    └─────────┬───────┘
                              │
                    ┌─────────▼───────┐
                    │ 通知业务方      │
                    │ 回滚完成        │
                    └─────────────────┘
```

**回滚时间**：
- 配置切换：< 5分钟
- 消费进度同步：< 10分钟
- 流量切回：< 5分钟
- 验证确认：< 10分钟
- 总计：< 30分钟完成回滚

### 6.8 迁移风险与应对

| 风险 | 应对策略 |
|------|---------|
| 协议兼容性问题 | 在阶段1充分验证；保留RocketMQ原生SDK接入路径；逐Topic验证功能对等 |
| 数据一致性差异 | 双轨运行阶段比对验证；抽样比对消息内容；消费进度同步机制 |
| 性能下降 | 监控对比前后性能指标；性能阈值告警；快速回滚机制 |
| 消费进度丢失 | 消费进度同步备份；回滚时进度恢复机制；消费者重启预案 |
| 业务中断 | 灰度切换（非一刀切）；核心Topic最后切换；回滚预案演练 |

## 7. 监控与可观测性设计

### 7.1 监控体系分层

```
第4层：业务监控
- Topic消息量趋势
- 业务延迟分布
- 业务成功率

第3层：应用监控
- SDK发送成功率
- SDK消费成功率
- SDK连接状态

第2层：代理层监控
- 协议处理成功率
- 请求延迟分布
- 连接数/活跃数
- 资源使用（CPU/内存/网络）

第1层：存储层监控
- 存储写入成功率
- 存储读取延迟
- 存储容量使用
- 存储健康状态
```

### 7.2 关键监控指标

**代理层指标**：

| 指标名称 | 说明 | 告警阈值 |
|----------|------|---------|
| proxy_request_total | 总请求量 | 无 |
| proxy_request_success_rate | 请求成功率 | < 99% 告警 |
| proxy_request_latency | 请求延迟P99 | > 100ms 告警 |
| proxy_active_connections | 活跃连接数 | 无 |
| proxy_connection_reject | 连接拒绝数 | > 0 告警 |
| protocol_parse_error | 协议解析错误数 | > 0 告警 |
| protocol_unknown_request | 未识别请求数 | > 0 告警 |
| topic_message_in_rate | Topic消息流入速率 | 无 |
| topic_message_out_rate | Topic消息流出速率 | 无 |
| topic_message_backlog | Topic消息积压 | 增长趋势告警 |

**存储层指标**：

| 指标名称 | 说明 | 告警阈值 |
|----------|------|---------|
| storage_write_success_rate | 写入成功率 | < 99.9% 告警 |
| storage_write_latency | 写入延迟P99 | > 50ms 告警 |
| storage_read_latency | 读取延迟P99 | > 100ms 告警 |
| storage_adapter_health | 适配器健康状态 | unhealthy 告警 |
| storage_adapter_error | 适配器错误数 | > 0 告警 |
| storage_capacity_used | 存储容量使用率 | > 80% 告警 |

**迁移验证指标**：

| 指标名称 | 说明 | 用途 |
|----------|------|------|
| migration_message_count | 迁移前后消息数比对 | 数据一致性验证 |
| migration_message_content | 迁移前后消息内容比对 | 数据完整性验证 |
| migration_consumer_offset | 迁移前后消费进度比对 | 消费状态验证 |
| migration_trace_match | 消息轨迹链路匹配 | 链路完整性验证 |

### 7.3 消息轨迹追踪设计

**追踪点**：
- 发送端：traceId生成、bornTimestamp、bornHost
- Proxy：receiveTime、proxyHost
- 存储层：storeTime、storeHost、msgId
- 消费端：pullTime、consumerHost、ackTime

### 7.4 迁移前后对比验证

**验证维度**：
1. 消息数量一致性：差异率 < 0.1% 通过
2. 消息内容一致性：抽样1000条消息，100%匹配通过
3. 消费进度一致性：offset一致通过
4. 性能对比：自研MQ延迟相当或更优通过

### 7.5 监控告警配置

| 级别 | 触发条件 | 响应动作 |
|------|---------|---------|
| P0（紧急） | 存储层完全不可用；发送成功率 < 90%；消费完全阻塞 | 立即电话通知；立即回滚 |
| P1（严重） | 发送成功率 < 99%；消费延迟持续上升；存储适配器异常 | 邮件+短信通知；启动排查流程 |
| P2（警告） | 发送成功率 < 99.9%；请求延迟 P99 > 100ms；存储容量 > 80% | 短信通知；关注监控 |
| P3（提示） | 新Topic接入提醒；配置变更提醒；非关键指标波动 | 仅记录 |
